# Curriculum — Deep Distributed Systems / Cloud / DevOps

This is the internals-level syllabus: a 12-module, build-and-break arc for a learner who already owns interview-level system design (CAP, sharding, consensus, locking as *vocabulary*) and wants the failure-mode boundary of each concept. The organizing bet is that the delta from interview-level to internals-level lives entirely in the corner cases — what linearizability forbids that sequential consistency permits, why Raft needs the commit-index restriction of §5.4.2, why 3PC's non-blocking claim dies under partition — and those are learned only by implementing the primitive and then breaking it under partition, clock skew, and crash. Reading modules do not teach this; a linearizability checker pointed at your own KV store does.

How this track fits the rest of Crucible: the modules and their canonical sources are the *content*; Crucible is the delivery engine that teaches, then tests, then schedules review. Per **[R6]** (see [`../07-landscape.md`](../07-landscape.md)), Crucible does **not** re-implement the hard distributed-systems autograders — it orchestrates over the best external ones and layers its own unique assessment on top. What that means concretely is spelled out below and drives the "Testable skills" column.

## The R6 stance for this track: labs are borrowed, defense is Crucible's

The graded *conformance* lab — "does your Raft actually satisfy the safety properties under an adversarial schedule?" — comes from an external autograder that already exists and is battle-tested:

- **MIT 6.824 labs** — the gold-standard build-Raft → build-KV → shard progression in Go, with an autograder that is itself adversarial (figure-8, unreliable-network, snapshot/log-compaction tests). This is the backbone for Modules 2–4.
- **Jepsen Maelstrom / Fly.io Gossip Glomers** — a workbench that hands you a network and a client workload and checks your node binary's message-level behavior; the Gossip Glomers challenge set (broadcast, g-counter, kafka-style log, txn) is the lower-friction on-ramp before the full 6.824 lab.
- **Jepsen / Elle / Porcupine** — linearizability and transactional-anomaly checkers used as the *acceptance test* for anything you build. Porcupine (Go) or a hand-rolled checker keeps you in-language; the full Jepsen stack is Clojure-heavy and should not become the blocker.

Crucible does not reproduce any of that. What Crucible *adds* on top — and the only graders it hand-rolls — are three things:

1. **Design-essay defense** (`llm_judge`, reference-grounded). After the lab passes `go test`, Crucible asks you to *defend* a specific design choice in prose, and the LLM-judge grades it against a shown reference under the **rejected-alternative rubric**: an answer that does not name the rejected alternative *and* its concrete failure mode *and* a number fails, regardless of how fluent it reads. The judge is hosted (Anthropic, metered in USD — see [`../04-grading.md`](../04-grading.md)); it may only lower or flag a verdict, never raise a deterministic test result.
2. **Capacity / back-of-envelope numeric derivation** — the **[R8]** question type: a worked-formula oracle checks a numeric answer against a computed reference *with tolerance* (deterministic, no judge needed). Little's Law, quorum-RTT latency, tail-amplification probability, storage-tier cost crossover — these have a right answer, and Crucible grades it as such.
3. **Spacing, interleaving, and mastery (θ) tracking** — the retrieval schedule across these 12 modules, so a Raft safety rule you defended in week 3 resurfaces for reconstruction in week 9. See [`../06-progress-model.md`](../06-progress-model.md).

So the "Testable skills" below deliberately mix **build** items (graded by the external lab / plain `go test` / `pytest`), **design-essay** items (Crucible's judge + rejected-alternative rubric), and **back-of-envelope** items (Crucible's numeric oracle). The build column is the borrowed lab; the essay and numeric columns are Crucible's reason to exist.

## Sequencing and language choice

Run Modules 1→12 in order — do not cherry-pick. Consistency (1) frames everything; consensus (2) and replication (3) are the machinery the middle modules coordinate state on top of; orchestration / IaC / cloud / reliability (9–12) only make sense once the state-coordination core is real. Skipping to Kubernetes and Terraform without the consensus foundation reproduces exactly the surface understanding this track exists to escape (K8s is a set of control loops over a Raft store — Module 9 is a payoff of Module 2, not an independent topic).

Language is assigned per module, deliberately:

- **Go carries the internals spine** (Modules 2, 3, 5, 6-build, 9-build, 12). Raft's reference implementations (etcd/raft, hashicorp/raft) and the 6.824 labs are Go; building Raft under `go test -race` closes the stated Go gaps (interfaces, error wrapping with `%w`, timers/tickers, generics) on load-bearing code rather than toy drills. The existing concurrency discipline (2PL, `@Version`, lock-free aggregation, `context`+`WaitGroup` in conclave) means goroutines/channels/select are *new syntax for a problem already solved*. This track is also the fastest route from Go-early-beginner to Go-fluent — see [`../curriculum/go.md`](../curriculum/go.md).
- **Python/FastAPI carries the application-tier patterns** (Modules 4, 8) — transactional outbox, idempotency keys, saga orchestration, RED instrumentation, SLO burn-rate math — where fluency is already deep, so attention stays on delivery semantics, not the language. The existing mypy-strict / pytest / respx harness discipline transfers directly to deterministic distributed tests with injected clocks and fault proxies (toxiproxy). See [`../curriculum/python.md`](../curriculum/python.md).

DDIA (Kleppmann) is the connective read across all 12 modules, but it must be paired with the **primary paper at every internals boundary** — DDIA deliberately abstracts away the implementation detail that is the whole point here. Raft's safety argument, Dynamo's sloppy-quorum + hinted-handoff + vector-clock reconciliation, Spanner's TrueTime commit-wait bound, Kafka's ISR / leader-epoch fencing each require the source. The repeatable module shape is **DDIA chapter → primary paper → build → adversarial verification**.

## Module table

| **1** | **Consistency Models & CAP/PACELC** — the frame for everything | Place linearizability / sequential / causal / eventual on one lattice and state what each *forbids* (the content is the gap between adjacent models); reframe CAP as the trivial corner case and PACELC as the operationally useful statement (the latency-vs-consistency tax paid *even with no partition*); kill the linearizability-vs-serializability conflation (recency of a single object vs transaction isolation — orthogonal). | **Design-essay:** argue causal+eventual over linearizable for a cart service, naming the accepted anomaly (concurrent add/remove reconciliation) and the rejected alternative (linearizable-via-consensus) with its latency cost. **Build:** wire Porcupine/Elle against a naive read-repair KV; produce a history that violates linearizability but satisfies sequential. **Back-of-envelope:** 3-region majority quorum read at 40ms one-way RTT — compute added p50 read latency and name the PACELC "EL" cost you just quantified. **Adversarial:** the minimal 3-op/2-client history distinguishing causal from sequential, and why no single-object test catches it. | DDIA ch.5/9; Abadi, *PACELC*; Jepsen analyses |

| **4** | **Distributed Transactions** — 2PC/3PC, sagas, outbox, idempotency | Understand precisely why 2PC blocks (coordinator dies post-prepare → participants in-doubt holding locks) and why 3PC's non-blocking claim fails under partition; build the practical replacement for distributed ACID (transactional outbox + relay, idempotency keys, saga orchestration/choreography with compensations); internalize exactly-once as a *transport myth* — real only as effectively-once = at-least-once delivery + idempotent processing. | **Build (Python/FastAPI):** outbox table + relay/CDC to Kafka + consumer idempotency-key dedup; prove no lost/dup message across a crash injected between DB-commit and publish. **Design-essay:** walk the 2PC in-doubt window; state exactly which failure causes indefinite blocking and why participant timeouts can't safely resolve it. **Back-of-envelope:** 5-step saga, 80ms/step, 2% per-step failure — end-to-end p50, expected compensation frequency, and the lock-hold-time argument for saga over 2PC. **Adversarial:** kill the relay mid-batch → at-least-once redelivery, then show the idempotency guard making it effectively-once vs the dual-write baseline's data loss. | DDIA ch.7/9; microservices.io outbox/saga; Gray & Lamport 2PC |
| **5** | **Time & Ordering** — logical/vector/hybrid clocks, TrueTime | See why physical clocks can't order distributed events (skew, NTP jitter), why Lamport gives a consistent total order while vector clocks give the causal partial order needed for conflict detection; understand HLC as the engineering sweet spot (causality + closeness-to-physical-time in bounded space) and Spanner's TrueTime + commit-wait as the alternative that buys external consistency with hardware instead of coordination; connect vector clocks to Dynamo reconciliation and CRDT merges. | **Build:** Lamport + vector clocks in Go; on a 3-node log produce two events vector clocks flag concurrent but Lamport falsely totally-orders. **Design-essay:** Spanner commit-wait — why waiting out 2ε guarantees external consistency and its throughput/latency price; name the rejected alternative (consensus on every commit). **Back-of-envelope:** TrueTime ε≈4ms — commit-wait overhead on single-key write throughput and the case for tightening ε with more time masters. **Adversarial:** 200ms clock skew on one node using physical timestamps → causality violation (effect before cause); fix with HLC. | Corbett et al., *Spanner*; Lamport, *Time/Clocks*; DDIA ch.8/9 |
| **6** | **Messaging & Streaming** — Kafka internals, log compaction, exactly-once, backpressure | Understand Kafka as a distributed, partitioned, replicated commit log: the ISR protocol, leader epochs for fencing zombie leaders, high-watermark advancement, log-as-source-of-truth unifying messaging and stream processing; master delivery-semantics reality (idempotent producer PID+sequence, transactions across partitions for read-process-write exactly-once, log compaction for changelog/KTable); treat backpressure and consumer-lag as flow-control/capacity, not a config knob. | **Build:** real Kafka read-process-write with transactional producer + `read_committed`; prove exactly-once by crash-injecting mid-transaction. **Design-essay:** how leader epochs stop a zombie leader truncating committed data after a partition — construct the pre-KIP-101 truncation scenario they fix. **Back-of-envelope:** 500K msg/s × 1KB, RF=3, 7-day retention — network bandwidth (produce+replicate), disk, and partition count for a 10K-msg/s/instance consumer. **Adversarial:** overload a slow consumer; distinguish the three responses (scale / drop-with-sampling / backpressure) and quantify each via Little's Law. | Kafka docs + KIP-101; DDIA ch.11; Kreps, *The Log* |
| **7** | **Caching & CDNs** — invalidation, coherence, thundering herd | Treat cache invalidation as the genuinely hard problem: write-through vs write-back vs write-around vs cache-aside and the staleness/coherence trade each makes, and why TTL-only is the honest default; master the stampede family (miss on a hot key → origin overload) and its mitigations (single-flight coalescing, XFetch probabilistic early expiration, negative caching); understand CDN mechanics (edge cache keys, purge-propagation latency, stale-while-revalidate as the availability-favoring choice). | **Build (Go):** single-flight coalescing in front of an expensive origin; load-test to show N concurrent misses collapse to 1 hit, and measure origin-QPS reduction. **Design-essay:** invalidation for a feed-ranking service — choose cache-aside+TTL+probabilistic-refresh over write-through, justified via write-amplification and staleness tolerance (name the rejected option). **Back-of-envelope:** 95% hit ratio, 50K req/s, origin p99 200ms — origin QPS, then the spike when a hot key expires and 5K miss at once (motivates coalescing). **Adversarial:** trigger a stampede on one hot key; apply XFetch and quantify the p99 origin-latency improvement. | DDIA ch.1/11; Vattani et al., *XFetch*; CDN/RFC 5861 stale-while-revalidate |

## Where "build from scratch" stops

The from-scratch ethos is load-bearing for the primitives and a time sink for the platforms. Draw the line explicitly: **build the container runtime and the Raft store from scratch** (Modules 2, 3, 5, 9-build) because the primitive *is* the learning target; **use real Kafka / Postgres / Kubernetes / Terraform** (Modules 6, 8, 9-study, 10, 11) and study their internals — reach for the tool where the tool is not the primitive. A from-scratch container is great; a from-scratch Kubernetes is not the learning target. Likewise, don't let a Clojure-heavy Jepsen setup become the blocker — Porcupine (Go) or a hand-rolled checker keeps verification in-language.

## Effort calibration (numbers, not adjectives)

- The Raft lab (Module 2) alone is **40–60 focused hours**, and the figure-8 safety test and log-compaction snapshot are where most people stall — not leader election. Budget the difficulty in the safety proofs and compaction, not the happy path.
- The irreducible core is the **M2→M3→M4 spine** (Raft → replicated KV → sharded/transactional KV). If time runs short, Modules 7/10/11 can be time-boxed shallower without breaking the arc; Modules 1–6 cannot.
- Full arc: roughly a **~4-month intensive** (all 12 deep) or a **~9-month part-time** run. This is a multi-month commitment; the failure mode is stalling in Module 2 and never reaching cloud/DevOps.

## Limitations / open questions

- **What a single-node lab does not prove.** Each module's build proves behavior *under the tested fault schedule*, not correctness in general. A passing Raft is "correct under the schedules 6.824 and your chaos suite exercised," **not formally verified** — do not label it "production-grade." State this in the per-module done-marker.
- **Exactly-once is the recurring myth trap** (Modules 4 and 6). Exactly-once *delivery* does not exist at the transport layer; effectively-once = at-least-once + idempotency. Verify it with a crash-injection test, don't assert it.
- **Race/nondeterminism oracles are probabilistic** (per **[R4]**): `go test -race` only reports interleavings it actually observes and has false negatives, and Go randomizes map iteration order — so any "expected: DATA RACE" or "differs across two runs" check in a lesson is reported as *probabilistic over many iterations*, never as a clean deterministic verdict.
- **Cloud labs incur real (small) spend.** Prefer free-tier + localstack / kind / k3d for Modules 9–11, but some canary/multi-AZ realism (Module 10) genuinely needs a real account.
- **Depth allocation is unresolved and depends on intent.** SRE/infra-leaning → weight Modules 8–12 heavier; distributed-systems-engineer-leaning → weight 1–6. Also open: single integrating capstone (the replicated KV threaded through M2–6–12, more résumé-worthy) vs 12 independent artifacts; target weekly hours; and preferred cloud (AWS, given the existing deploy-guide experience, vs GCP where the Spanner/Borg papers land closest).
