# Python / FastAPI / Pydantic / asyncio — internals syllabus

This is the Python track's teach-then-test syllabus: a nine-module, internals-first curriculum for an engineer already fluent in Python who wants **mechanism, not basics** — the pydantic-core Rust boundary, the event loop's scheduling machinery, GIL release semantics, the descriptor protocol, mypy's variance rules, and the greenlet seam under async SQLAlchemy. It routes into the shared assessment model in [`../05-content-model.md`](../05-content-model.md) and the prototype feature spec in [`../02-features.md`](../02-features.md).

## The altitude asymmetry: Python is adversarial from day one

The Go track (`../curriculum/go.md`) is an **on-ramp** — it starts idiom-first at a calibrated-beginner altitude because `conclave` is his only real Go and the goal is fluency before depth. Python is the mirror image. It is one of his deepest languages (OpenTrace ~27K LOC, JobAggregator ~6.7K LOC, both FastAPI + pydantic + asyncio), so a fluency on-ramp would teach him nothing he doesn't already ship daily. The only assessment worth his time here is **adversarial from the first item**: not "can you write a validator" but "trace `Model(**data)` down to pydantic-core and back, and say where a `mode='before'` validator runs relative to type coercion." Every module is pitched at the seam where a fluent user's mental model is usually *wrong or absent* — the compiled Rust core he treats as a black box, the `CancelledError` that is thrown into a coroutine rather than returned, the `MissingGreenlet` that reveals how un-async "async" SQLAlchemy really is.

Rejected alternative: **a progressive Python track that ramps basics→intermediate→advanced** (the shape the Go track takes). Rejected because the ramp's first two-thirds land below his floor; the retrieval effort — the entire pedagogical point per [`../05-content-model.md`](../05-content-model.md) — only exists at the internals altitude. Starting deep is not gatekeeping; it is where the desirable difficulty actually lives *for this learner*.

## The gate and the hidden-test battery

Two enforcement mechanisms make "deep from day one" testable rather than aspirational:

- **`mypy --strict` with zero `# type: ignore`** is the always-on correctness gate, not a module topic. A repository/DI layer that passes at default mypy but leaks `Any` through an untyped decorator *fails* here, and the failing strict flag must be named. This mirrors the ruff + strict-mypy + pytest gate already on his real repos; Crucible just makes passing it a graded outcome. Rejected alternative: **default mypy** — rejected because it silently admits `Any` at exactly the generic-boundary seams (Module 4) where his real bugs would hide.
- **Hidden unit + property batteries** (pytest + hypothesis) grade code items deterministically per the routing table in [`../05-content-model.md`](../05-content-model.md). The learner's code runs against tests he cannot see; a hand-picked happy-path example is not enough, because hypothesis shrinking hunts the minimal counterexample his example missed. Rejected alternative: **visible reference tests** — rejected because they let him code to the test rather than to the invariant, which is precisely the shallow-understanding failure this track exists to expose.

Per R5, code items grade **asynchronously** against a warm runner so a multi-second pytest+hypothesis run never stalls a 25-minute session; grading-latency p50/p90/p99 is tracked as a health metric.

## The spine: one repo, no isolated toy topics

Every module contributes a load-bearing slice to a **single deliverable** — a typed, async, pydantic-v2 FastAPI backend with an async SQLAlchemy 2.0 data layer (aiosqlite in tests, asyncpg-ready), one SSE and one WebSocket endpoint, gated by ruff + `mypy --strict` + pytest + hypothesis. This is deliberately the shape of JobAggregator and OpenTrace's FastAPI+SSE backends, so no internals topic is studied in a vacuum: descriptors (Module 5) are the mechanism under pydantic field objects; the generator `send`/`throw` protocol (Module 6) *is* what the event loop drives (Module 3); the greenlet seam (Module 9) is the same class of teardown bug as SSE disconnect-mid-stream (Module 2).

**Recommended sequence** (mechanism before application): **5 → 6 → 3 → 4 → 1 → 2 → 9**, with **7** (packaging) and **8** (testing) threaded throughout as the gate. Rationale: `await` in Module 3 is unintelligible as mechanism until the coroutine `.send()` protocol from Module 6 is owned; typing (4) precedes the pydantic/FastAPI/DB applied stack (1→2→9) so the generic seams are typed correctly the first time. Rejected alternative: **the "useful first" order (1→2→9 pydantic→FastAPI→DB up front)** — rejected because it teaches the applied APIs before the machinery that explains their surprising behavior (why `mode='after'` sees siblings, why `await` yields, why lazy-load raises under async), reducing internals to memorized rules instead of derivable ones.

## Assessment stance

Two item shapes only, per the recommendations: **(a) reimplement the primitive** (`property` as a descriptor; an event-loop driver that calls `coroutine.send`; a minimal DI resolver) or **(b) predict-then-measure** (the `__slots__` memory delta, v2-vs-v1 throughput, N+1 query counts under `EXPLAIN`). Every "why" item requires the **named rejected alternative in writing** — metaclass vs `__init_subclass__`, Protocol vs ABC, `BackgroundTasks` vs queue, `gather` vs `TaskGroup`, `joinedload` vs `selectinload` — because that pairing is his engineering tell and the fastest way to surface shallow understanding.

The Correctness>Reliability ranking is enforced in the rubric: a module is "done" only when its **failure mode is demonstrated with a test** (cancelled-task cleanup, `MissingGreenlet` on lazy load, the freezegun import-capture trap), not merely described. Every claim stays quantified — p50/p99 deltas, bytes/instance, query counts, iteration counts — never "faster" or "less memory."

## Limitations / open questions

- **This is curriculum design, not re-verified external fact.** Version-specific API names (pydantic-core internals, `asyncio.timeout()` at 3.11+, SQLAlchemy 2.0 surface) reflect the training-cutoff model and must be re-checked against the exact versions pinned in his `uv.lock` before any item relies on a specific name. Per R10, toolchain pins are per-track and a periodic "gate against latest" job catches a bump turning green lessons red.
- **The GIL answer is a moving target.** Free-threaded / no-GIL CPython (PEP 703, 3.13+ experimental) changes "what the GIL blocks." Module 3 teaches the current model **and** flags the direction of travel, rather than a soon-stale absolute — otherwise the threads-vs-processes derivation ages badly.
- **Modules 5 and 6 risk becoming trivia** (metaclasses; generator `send`/`throw`) if divorced from the spine. They earn their place **only** as the mechanism under descriptors/framework fields and under `await`; the parts that don't connect to the FastAPI+SSE spine should be dropped, not taught for completeness.
- **The greenlet seam (Module 9) is the highest-value and highest-frustration topic** — budget extra time. The `MissingGreenlet` / detached-instance / lazy-load-in-serializer cluster is where "it worked in the test" async backends actually break in prod, and where an aiosqlite-green suite proves the least about asyncpg.
- **Open, needs his call:** (1) target depth — reimplement-the-primitive (roughly 2× time/module) vs read-and-reason about CPython/library source? (2) Is a Docker Postgres in scope, since pooling/statement-caching lessons only land against real asyncpg? (3) Does packaging (7) stop at reproducible local envs, or extend to wheel-build + publish + CI? (4) A capstone that deliberately induces each failure mode (cancellation leak, N+1, double-serialization, `MissingGreenlet`) and requires an adversarial test proving the fix — the multi-agent audit style he already runs on his own repos?
